# 需求：Docker 应用 Compose 面板

日期：2026-08-21

## 一屏摘要

- 目标：在已登录的宿主面板上，把本插件零配置、按 Agent 独立部署，并用 compose 管理该 Agent 上的应用（R1、R11）
- 使用者：面板管理员；`local` 与远程 Agent 均可，NAT 后只要能连控制面即可被管理（R1、R11、R12）
- 范围：每台 Agent 独立零配置安装、统一面板操作、compose 部署、`./` 映射、启停与日志、版本与 latest 更新、对外端口一键挂 HTTP 规则；宿主仓库可改为满足这些行为（R2–R6、R11、R12、R14）
- 关键规则：不限 `local`；执行只在目标 Agent 本机；管理员不直连 Agent、不暴露 Docker 接口；`./` 不得拦住部署；默认不自动更新；HTTP 规则仍属宿主；Docker API 不做成插件权限（R3、R5、R6、R7、R11、R12）
- 成功标准：任意在线 Agent（含非 `local`、含 NAT）装上插件后，可在统一面板完成 compose 部署与运维，且无需填写 Docker 连接或授予 Docker API（R2–R7、R11、R12）
- 不做事项：完整 Docker 控制台、导入已有容器、Agent 对外独立入口、资源组主界面、仅限 `local`、不改 accelerator-sources / cloudflare-dns 的部署范围（R8、R9、R10、R13、R15）

## 完整需求

### R1 面板目标与使用者

管理员在已登录的宿主面板中，选择一台已安装本插件的 Agent，管理该 Agent 上的 Docker 应用。每个应用对应一份 docker-compose 定义，可部署、运维、看版本、给对外端口挂 HTTP 访问。本插件不是 Docker 引擎总控台，也不再以「镜像名 + 规则引用」作为用户主路径。操作入口在统一面板，不要求管理员打开 Agent 自己的地址。

验收：

- 管理员打开本插件后，先能选择或确认目标 Agent，再看到该 Agent 上由本插件部署的 compose 应用列表，而不是仅含镜像名和规则引用的配置表。
- 未把本插件部署到某台 Agent 时，不能在该 Agent 上部署或改动这些应用。
- 完成部署、启停、看日志、更新、挂 HTTP 规则时，不要求浏览器访问 Agent 的 IP 或独立端口。

### R2 用 compose YAML 部署应用

管理员通过粘贴或编辑 docker-compose YAML 创建和更新应用。一份 YAML 对应一个应用（可含多个 service）。部署使用 YAML 中的 `image` 拉取并运行镜像，运行位置是当前选中的 Agent 本机。该 Agent 上 Docker 引擎未就绪时不能部署，并给出明确提示。保存 YAML 后再次部署，运行中的应用与当前 YAML 一致。

验收：

- 给定一份合法、仅使用 `image` 的 compose YAML，管理员可以在选中的 Agent 上创建应用并部署成功，该 Agent 的应用列表中出现该应用。
- 修改 YAML 中的镜像、端口、环境变量或卷并再次部署后，该 Agent 上运行中的服务与新 YAML 一致。
- YAML 非法或缺少可部署的 `image` 时，部署失败并显示可理解原因，已有应用保持原状。
- 目标 Agent 上 Docker 引擎不可用时，部署入口不可用或提交后失败，并提示引擎未就绪。

### R3 `./` 相对路径映射

每个应用在其 Agent 上有独立工作目录。compose 中的相对绑定（如 `./data:/data`、`./config.yml:/app/config.yml`）相对该工作目录解析，并作为正常卷映射执行。相对路径绑定不得仅因是主机路径而被拒绝或要求额外确认才能部署。

验收：

- 部署含 `./data:/data` 的 compose 后，容器内 `/data` 对应该 Agent 上该应用工作目录下的 `data`；向其中写入的文件在该工作目录中可见。
- 部署含相对文件绑定的 compose 后，容器能读到该工作目录中对应路径的文件内容。
- 仅因使用 `./` 或其它相对绑定而拒绝部署，视为不满足本条。

### R4 启停、状态与日志

已部署应用可启动、停止、重启、删除。面板展示每个应用及其 service 在目标 Agent 上的运行状态。管理员可查看各 service 的日志。删除后该应用不再出现在该 Agent 的本插件管理列表，其 compose 部署被拆除。

验收：

- 运行中的应用可停止；停止后状态为已停止，对应容器不再提供服务。
- 已停止的应用可启动；启动后状态为运行中。
- 运行中的应用可重启；重启后仍为运行中，服务可再次访问。
- 管理员选择某个 service 后能看到该服务产生的日志文本。
- 删除应用并确认后，列表中不再有该应用，且其容器不再运行。
- 删除未确认时，应用与运行状态不变。

### R5 版本展示与 latest 更新

面板展示每个应用当前运行的镜像版本，至少包括 tag。有 digest 时同时展示 digest（可缩短）。tag 为 `latest` 或其它浮动标签时，仍应能发现仓库中更新的镜像并执行更新：拉取当前 tag 指向的镜像，若与运行中 digest 不同则切换到新镜像。默认不自动更新。检测到可更新时显示「有新版本」，由管理员点击更新。

验收：

- 运行 `nginx:1.27` 一类固定 tag 时，面板显示该 tag；有 digest 时同时能看到当前 digest。
- 运行 `nginx:latest` 时，面板显示 `latest`（及 digest，如有）；不会因为 tag 是 `latest` 而隐藏版本或禁用更新。
- 仓库中同一 tag 的 digest 已变化时，面板显示「有新版本」；管理员点击更新后，运行中 digest 变为新值，应用恢复可用。
- 仓库 digest 与运行中相同时，不显示「有新版本」，点击更新也不会无故拆掉后仍停在不可用状态。
- 未点击更新时，即使存在新 digest，运行中应用也不会自行换成新镜像。

### R6 对外端口一键挂 HTTP 规则

应用中已发布到该 Agent 主机的端口，应能在应用页直接挂宿主 HTTP 规则：管理员填写入口域名（协议与域名的填法与现有 HTTP 规则一致），后端地址由该发布端口自动带上，不必再去 HTTP 规则页手工填写容器地址。创建成功的规则出现在宿主「流量管理 → HTTP 规则」中，启用后通过该域名可访问对应服务。本插件不另建一套独立路由引擎。

验收：

- 应用发布了主机端口后，应用页能列出这些端口，并提供挂 HTTP 规则的入口。
- 管理员选择一个发布端口、填写入口域名并保存后，宿主 HTTP 规则列表中出现对应规则，后端指向该 Agent 上该端口的服务。
- 规则启用且域名解析到该 Agent 后，用该入口域名可以访问到该应用对应端口的 HTTP 服务。
- 没有发布端口的应用不提供挂 HTTP 规则的入口，或明确提示没有可挂的端口。
- 未填写入口域名时不能创建规则；已有 HTTP 规则与应用状态不变。

### R7 Docker API 不做插件权限

管理员使用本插件部署、启停、看日志、更新应用时，不需要为 Docker API 或同类 Docker 能力单独授权。能否调用 Docker 只取决于目标 Agent 本机引擎是否可用，以及该管理员是否可以使用本插件。创建 HTTP 规则仍使用宿主已有的 HTTP 规则能力，不把 Docker 接口拆成可授予/可收回的插件权限项。

验收：

- 可以使用本插件的管理员，在目标 Agent 的 Docker 引擎就绪时，无需再打开或授予任何 Docker API 权限项即可完成 R2–R5。
- 面板上不出现需要为「Docker API / Compose API / 容器管理 API」单独勾选才能部署的授权步骤。
- 无本插件使用权限的人仍然不能部署或改动这些应用。

### R11 按 Agent 独立零配置部署

本插件按 Agent 独立部署，与资源加速插件一样：每台要使用的 Agent 各自安装一份，不限 `local`。把本插件部署到一台 Agent 时，管理员不必填写 Docker 主机地址、套接字路径、API 密钥或其它 Docker 连接参数。部署成功后，该 Agent 使用本机 Docker 引擎；随后即可在统一面板上管理该 Agent 上的 compose 应用。可选的镜像加速等项不得成为首次部署的必填项。未安装本插件的 Agent 不受影响。

验收：

- 管理员可以把本插件部署到 `local` 以外的在线远程 Agent，无需填写任何 Docker 连接字段。
- 只把插件装到 Agent A 时，不能在 Agent B 上部署或改动本插件的 compose 应用。
- 该 Agent 本机 Docker 已就绪时，部署完成后即可列出应用并执行 R2，不必再做第二步连接配置。
- 该 Agent 本机 Docker 未就绪时，插件仍可完成部署，但应用部署按 R2 提示引擎未就绪，而不是要求补填 Docker 连接。
- 交付不得把本插件限制为只能安装在 `local`。

### R12 统一面板可达与本机执行

管理操作一律走管理员已经登录的宿主面板。Compose 的拉取、运行、日志和更新只在目标 Agent 本机执行。Agent 位于 NAT 或内网、控制面不能主动连上该 Agent 时，只要该 Agent 能连接控制面，管理员仍能在统一面板上管理它。不得把 Docker 引擎接口作为网络服务暴露给面板、其它 Agent 或公网。

验收：

- 管理员仅访问控制面面板地址即可完成 R2–R6、R11；不需要 Agent 有公网 IP，也不需要给 Agent 额外放行 Docker 或管理端口。
- 一台只能主动访问控制面、入站不可达的 Agent，在插件已部署且 Docker 就绪时，仍能被统一面板部署 compose 应用。
- 从面板所在网络扫描该 Agent 时，不存在可匿名或凭面板会话之外的凭证直接调用的 Docker 接口。

### R14 允许修改宿主以满足本需求

R1、R11、R12 的可观察行为必须成立。若当前宿主还不能把 Agent 上的本插件操作挂到统一面板，或不能按 Agent 零配置下发本插件，允许修改主仓库 `nginx-reverse-emby`。不得以「只改插件仓库、宿主不动」为由，把能力收缩成仅 `local` 或必须直连 Agent。

验收：

- 远程非 `local` Agent 在插件已部署且 Docker 就绪时，能在统一控制面面板上完成 R2–R6，不要求该 Agent 有公网管理入口。
- 不存在「宿主未改，因此本插件只能装在 `local`」的交付结论。

## 不做事项

### R8 不做完整 Docker 控制台

不提供对本机任意容器、镜像、卷、网络的总览与管理。不把 Portainer 一类引擎控制台纳入本插件。

验收：

- 交付界面没有「本机全部容器 / 镜像 / 卷 / 网络」管理页。
- 不是本插件用 compose 部署的容器，不会作为可管理应用出现在本插件列表中。

### R9 不导入已有容器，不以 docker run 为主路径

不把本机已有、非本插件部署的容器导入成应用。管理员主路径是 compose YAML，而不是粘贴 `docker run` 或认领未纳入 compose 的容器。

验收：

- 本机先用其它方式启动的容器，不会在本插件中出现「导入 / 认领」主流程。
- 创建应用的主入口是 compose YAML，而不是 `docker run` 命令框。

### R10 本轮明确不做的运维与编排能力

本轮不做：面板内 `build` 构建镜像、容器终端、CPU/内存图表、应用商店或模板市场、应用工作目录的文件上传/编辑器、默认自动更新、Swarm/Kubernetes。相对路径工作目录随部署创建；目录内文件可通过 SSH 等本轮范围外的方式放入。

验收：

- 交付中没有 build、终端、资源图表、应用商店、工作目录文件管理的主功能入口。
- 新应用默认不会在未点击更新的情况下自动换成新镜像。
- 文档与界面不声称支持 Swarm 或 Kubernetes。

### R13 不做 Agent 直连控制台，也不做控制面资源组主界面

不把本插件做成必须打开 Agent 独立网址才能操作的控制台。也不把本插件的主界面做成 Cloudflare DNS 那种控制面资源组目录；应用按 Agent 管理，不按资源组隔离一套独立对象。

验收：

- 交付不要求、也不引导管理员为使用本插件而去访问 `http(s)://<Agent地址>:<管理端口>` 一类独立入口。
- 本插件主界面不是控制面「资源组」列表，也不以资源组作为创建应用的必选隔离层。

### R15 不改造对照插件的部署范围

本需求不改变资源加速（`accelerator-sources`）与 Cloudflare DNS（`cloudflare-dns`）的部署范围。资源加速继续按 Agent 独立部署；不把 Cloudflare DNS 改成按 Agent 安装，也不把二者改成仅 `local`。

验收：

- 交付后，资源加速仍可按 Agent 独立部署，而不是只能装在 `local`。
- 交付不包含把 Cloudflare DNS 改为 Agent 插件或仅 `local` 安装的行为变更。

## 来源

- 用户对 `plugins/docker-app` 的结果：compose 直接部署且允许 `./` 映射；对外端口方便挂 HTTP 规则；面板看版本且 `latest` 可更新；Docker API 不必做成权限；插件零配置、按 Agent 独立部署。
- 用户确认面板位置可按安全性与 NAT 可达性选择：采用统一宿主面板操作、Agent 本机执行，不采用 Agent 对外独立控制台，也不采用 Cloudflare DNS 的资源组主界面。
- 用户更正：资源加速保持每台 Agent 独立部署，不纳入本需求；为实现统一面板与零配置下发，允许修改主仓库 `nginx-reverse-emby`（R14、R15）。
- `plugins/docker-app/README.md`、`plugins/docker-app/config.schema.json`：当前实现是镜像与规则引用登记、效果依赖宿主授权句柄，与上述结果不一致。
- 宿主文档 `guides/agents.md`、`getting-started/core-concepts.md`：Agent 主动连接控制面，控制面不主动连接 Agent，NAT/内网 Agent 只要能访问控制面即可工作（R12）。
- 宿主文档 `guides/http-rules.md`：HTTP 规则仍按域名转发到后端；本插件只提供从应用发布端口创建该规则的便捷入口（R6）。
- Dockge 等 compose 优先 Web UI 的常见能力：每应用目录与相对绑定、YAML 编辑、启停与日志、按 digest 更新浮动标签。
- Portainer Agent / Edge Agent 一类实践：不把 Docker 接口暴露到网络，NAT 节点由节点主动连回管理面（R7、R11、R12）。
